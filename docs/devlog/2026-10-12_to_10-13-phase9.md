# 2026-10-12 ~ 2026-10-13 — Phase 9: Beta 이후 Final Launch 준비

Public Beta 이후 Site는 owner-only로 전환하고 Final Launch 준비에 들어갔다.

## Phase 9A — Works ↔ News

### 출발점은 실제 사용 UX
Beta 이후 사용하면서 다음 요구가 명확해졌다.

1. desktop의 왼쪽 news stack은 오른쪽으로, 오른쪽 stack은 왼쪽으로 펼쳐져야 한다.
2. Works를 보고 있을 때 관련 뉴스를 바로 보고 싶다.
3. News에서도 특정 Work 기준으로 필터링하고 싶다.
4. 기능은 늘리되 과한 “AI/SaaS 느낌”의 UI는 피한다.

첫 수정:

`22797915 — Fix directional news stack expansion`

대표 card 위치는 고정하고 secondary layers만 adjacent column 방향으로 fan되도록 바꿨다. mobile/coarse pointer는 기존 compact source strip을 유지했다.

### 관계를 Story에 저장할지 Article에 저장할지
작품과 뉴스 연결을 만들 때 핵심 설계 선택은 관계의 source of truth였다.

Story는 durable entity table이 아니라 Article topic을 기반으로 projection된다. 또한 하나의 Story 안에서도 기사별로 관리자가 잘못된 관계를 제외할 필요가 있다.

그래서 Article-level many-to-many를 선택했다.

`7e2e3463 — Add article-work relations and backup v2`

`article_work_relations`:

- article_id
- work_id
- state = linked / excluded
- origin = automatic / manual

특히 `excluded`는 manual만 허용한다.

자동 matching은 conservative하게:

- 한국어/원제 normalize
- safe title prefix
- generic “Star Wars” 제외
- ambiguous season skip
- 추가 AI call 없음

으로 제한했다.

Manual state가 존재하면 자동 재검사는 덮어쓰지 않는다.

### Public에서는 Story 단위로 다시 합침
관계는 Article에 있지만 사용자에게 related count를 Article 수로 보여주면 같은 사건을 여러 매체가 보도한 만큼 숫자가 부풀어 오른다.

따라서 public projection은:

```text
Article relations
→ Story member union
→ unique Story count
```

을 사용한다.

`6d8f0531 — Connect Works and News archives`

결과:

- News: Work filter
- Works: `관련 소식 N`
- 최대 8개의 최근 Story row dialog
- “뉴스 아카이브에서 모두 보기”
- admin: Article별 관련 작품 편집
- maintenance: 기존 Article 관계 재검사

실제 Production backup v2에서는 `article_work_relations` 41개가 확인됐다.

Ahsoka Season 2는 Article 관계가 8개였지만 public 관련 소식은 **4 Story**로 dedupe되어 UI의 “관련 소식 4건”과 일치했다.

이것이 Article-level relation + Story-level presentation을 선택한 이유를 실제 데이터로 확인한 사례다.

### Backup v2
새 durable relation table이 생겼으므로 Backup v1의 의미를 몰래 바꾸지 않고 v2를 만들었다.

historical v1은 계속 validate/plan 가능하며 relation 0건으로 해석한다.

## Phase 9B — Final-Launch Featured Work Hero

### 처음 계획
Desktop Featured만 포스터 왼쪽 + 작품 상세 정보 오른쪽의 information-rich hero로 만들기로 했다.

추가 metadata:

- creator/director
- principal cast
- synopsis
- release context

기존 Featured 선정 규칙은 변경하지 않는다.

### 모바일에서 즉시 발견한 UX 문제
Desktop 상세 Hero를 mobile에서 그대로 세로로 쌓으면 Featured 하나가 화면 대부분을 차지한다는 문제가 대화 중 바로 제기됐다.

그래서 구현 전에 mobile interaction을 바꿨다.

```text
Desktop
→ persistent detailed hero

Mobile
→ compact horizontal preview
→ one tap
→ detail dialog
```

실제 구현:

`d7c522c2 — Add Featured Work metadata and backup v3`

`456f4d52 — Build responsive Featured Work hero`

mobile preview poster는 104px, dialog는 최대 `85dvh`, `max-width: 520px`, 내부 scroll을 사용한다.

관련 소식/예매가 또 다른 modal을 위에 쌓지 않도록 하나의 dialog에서:

- detail
- news
- ticket

mode를 전환한다.

### Metadata 원칙
새 필드는 모두 nullable.

- `creator_credit`
- `principal_cast`
- `synopsis`
- `release_context`

정보가 없으면 “미정”을 억지로 출력하지 않고 해당 row를 숨긴다.

TMDB는 여전히 runtime dependency가 아니며, 신규 credit 자동 채우기는 이 Phase에서 보류했다.

### Backup v3
Works row shape가 바뀌었으므로 v3를 만들었다.

v1/v2 artifact의 Work에는 새 metadata가 없으므로 dry-run target에서는 null default로 명시한다.

restore executor는 여전히 추가하지 않았다.

## Phase 9C — Grounded AI Assistant Design

`b105cabd — Design grounded HOLOCRON AI Assistant`

이 Phase에서 가장 중요한 결정은 **구현하지 않는 것**이었다.

9C는 documentation-only design phase로 두고 current `COMING SOON`을 유지했다.

### 일반 chatbot이 아닌 archive assistant
두 경험만 MVP로 정의했다.

#### Archive Q&A
현재 HOLOCRON public archive의 title/summary/source/date/Work relation을 근거로 답한다.

#### Script Planner
```text
topic/request
→ candidate Stories
→ user selects Stories
→ review exact evidence
→ generate cited facts/caveats/outline/optional draft
```

사용자가 Story를 고르기 전에 숨은 retrieval만으로 긴 대본을 바로 생성하지 않는다.

### 의도적으로 제외한 것
- embeddings
- vector DB
- runtime article scraping
- web search
- AI reranking
- full article ingestion
- durable conversation history

### Retrieval
- candidate 최대 12 Story
- Q&A evidence 최대 6 Story
- Script는 user-selected 1~8 Story
- Story별 model evidence Article 최대 3

deterministic Work relation + title/summary matching을 우선한다.

### Security
Article title/summary/admin text도 **instruction이 아니라 untrusted data**다.

client가 보낸 title/summary/URL을 AI evidence로 믿지 않고 Story ID를 받아 server가 D1에서 다시 읽는다.

생성 전후로 evidence state가 바뀌었는지도 확인하는 freshness receipt 설계를 포함했다.

### Persistence
MVP에서:

- chat transcript 저장 안 함
- generated answer 저장 안 함
- selection history 영구 저장 안 함

으로 설계했다.
