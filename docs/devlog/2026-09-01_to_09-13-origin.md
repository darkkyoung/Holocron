# 2026-09-01 ~ 2026-09-13 — Prototype에서 V2로

> 상태: 초기 부분은 대화 기반 복원. 2026-09-13부터 canonical history로 교차 확인 가능.

## 09-01 — 모바일 대응을 먼저 해결하려다

초기 HOLOCRON은 이미 뉴스 카드를 보여주는 prototype이 있었고, 당시 작업 기준은 `feature/topic-cards`였다. 모바일에서 깨지는 UI를 먼저 손보되 HTML 구조는 크게 바꾸지 않고 CSS 중심으로 해결하자는 요구가 있었다.

이 시점의 중요한 판단은 “동작하는 desktop 구조를 모바일 때문에 다시 뜯지 않는다”였다. 아직 제품 구조가 빠르게 변하는 단계였으므로 대규모 UI rewrite보다 좁은 범위의 responsive 수정이 적절했다.

## 09-02 — CSS 누적과 SWNN 문제

당시 `style.css`에는 이전 수정이 계속 누적되어 중복과 override가 많았다. 전체 CSS를 처음부터 정리하는 선택지도 있었지만, 아직 기능이 자주 바뀌는 prototype에서 전면 정리는 리스크가 컸다.

그래서 전술적으로 파일 하단에 모바일 전용 override를 두는 방식을 택했다.

목표는 다음과 같았다.

- 뉴스 카드 1열
- 검색 UI 세로 정렬
- 탭/필터의 가로 스크롤
- touch target 확대
- 관리자 버튼 wrap

동시에 SWNN 수집은 안정적이지 않아 **일단 제외하고 나중에 해결되면 다시 활성화**하는 방향을 택했다. 이 결정은 나중에 SWNN을 영구 포기한 것이 아니라, 불안정한 한 source가 전체 개발을 막지 않게 하기 위한 임시 격리였다.

이때 이미 훗날의 중요한 원칙 두 가지가 보였다.

1. 한 source 실패가 전체 pipeline을 막아서는 안 된다.
2. 구조 문제를 계속 override만 쌓아 해결하면 언젠가 한계가 온다.

## 09-09 — 개발 방식 자체가 병목이라는 인식

사용자는 개발 속도가 예상보다 느리다고 느꼈다. 당시 흐름은 ChatGPT가 코드를 설명하면 사용자가 개발 환경에서 직접 파일을 열고 수정하고, 오류를 다시 가져오는 방식이었다.

문제는 코딩 능력 자체보다 **중계 비용**이었다.

- 파일 탐색
- 코드 복사/붙여넣기
- 명령 실행
- 오류 전달
- 다시 수정

이 반복이 전체 속도를 낮췄다.

그래서 역할을 나누는 개발 방식이 제안됐다.

```text
ChatGPT / planning agent
→ 명세·아키텍처·acceptance 기준

Coding agent / Codex
→ repository 직접 분석·수정·테스트

ChatGPT
→ 결과 검토·다음 단계 설계
```

이후 HOLOCRON 개발에서 “강한 모델은 설계와 검토, coding agent는 repository 작업”이라는 패턴이 반복적으로 사용됐다.

## 09-13 — 현재 HOLOCRON의 제품 정의가 잡히다

이날 프로젝트의 핵심이 훨씬 명확해졌다.

### 제품 목표
한국 팬이 여러 해외 매체를 돌아다니지 않고 Star Wars 뉴스를 한 곳에서 볼 수 있는 **한국어 뉴스 아카이브**.

### 소스 정책의 초안
핵심 후보는 다음 일곱 곳이었다.

- StarWars.com
- Star Wars News Net
- Collider
- The Hollywood Reporter
- Deadline
- Variety
- Forbes

논의가 진행되며 정책은 다음 형태로 굳어졌다.

- StarWars.com / SWNN은 Star Wars 중심 source이므로 폭넓게 수집
- 나머지 일반 매체는 Star Wars 관련성이 명시적으로 있는 기사만
- Review / Character Spotlight 같은 형식은 public archive에서 제외하거나 review로 돌림

### 90일 archive
처음에는 “최근 2~3개월”이라는 표현이었고, 구현 규칙으로 **90일**을 선택했다. HOLOCRON은 모든 역사적 Star Wars 뉴스를 무한히 보관하는 서비스보다, 최근 흐름을 빠르게 이해하는 서비스에 가깝게 시작했다.

### 같은 사건은 겹친 카드로
여러 매체가 같은 사건을 다뤘을 때 동일한 카드를 반복해서 세로로 나열하는 대신 physical card stack처럼 겹쳐 보이게 하는 아이디어가 나왔다.

- 최초 게시/가장 이른 확인 기사 = 대표
- 추가 보도 = 뒤에 겹친 카드
- desktop = hover/fan
- mobile = 별도 touch interaction

이 시점에 HOLOCRON이 단순 RSS reader가 아니라 **Story 중심 archive**가 되기 시작했다.

### 관리자 workflow
자동 수집이 잘못 묶거나 불필요한 기사를 넣을 수 있으므로 다음 관리 기능이 처음부터 중요하게 잡혔다.

- 같은 주제로 묶기
- 주제 묶음 해제
- 뉴스에서 제외
- 복구

나중에 title override까지 더해지면서 “관리자의 판단은 자동화보다 우선한다”는 제품 원칙으로 발전했다.

## V1을 계속 고치지 않고 V2를 만들기로 한 이유

같은 날 기존 `HolocronArchive_Latest`가 수동 기능 추가로 점점 덕지덕지해지고 있다는 문제를 명확히 인식했다.

V1은 빠른 prototype으로 유용했지만 대략 다음 문제가 있었다.

- Flask 중심
- JSON 기반 mutable state
- subprocess 의존
- 큰 `app.py`
- UI/수집/AI/데이터 책임 혼재

“1호의 좋은 기능을 가져오되 구조적 스파게티는 가져오지 않는다”는 방향으로 새 `Holocron` repository를 사실상 V2 rewrite로 추진했다.

새 기반은:

- TypeScript
- React
- Cloudflare Worker/Sites
- Cloudflare D1
- Drizzle
- OpenAI API

였다.

그리고 agent가 빠르게 코드를 만들어도 프로젝트가 다시 무너지지 않게 지속 규칙이 필요하다는 요구가 나왔다.

그 결과 09-13 canonical에:

`5fa58c43 — Add agent development rules to AGENTS.md`

가 들어갔다.

## 이 시기의 의미

초기 2주는 기능보다 더 중요한 것을 결정했다.

- “한국어 Star Wars 뉴스 archive”라는 제품 정체성
- Story grouping
- 90일 범위
- administrator override
- source isolation
- agent가 지켜야 할 architecture boundary

이후 거의 모든 Phase가 이 원칙 위에서 확장됐다.
