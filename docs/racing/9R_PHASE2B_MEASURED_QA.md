## 구현 범위

`galactic-racing-0.5.0`: 실제 진입점에서 seeded 판정 → 분기 거리대로 연속 주행 → 접선이 맞는 합류. 실패는 본선 유지. 순위에 쓰는 진행도와 실제 공간 경로를 연결했으며, v0.4의 순간 거리 보너스는 v0.5에 적용하지 않는다. 본선 없는 지름길 이벤트와 진입 전 이벤트를 차단한다.

예선은 기존 랩 엔진을 재사용한 8명 × 3회다. 한 라운드 내부 중첩 출발을 유지하면서 전원 완주 후 12초 결과 발표를 거친다. 프리쇼와 최종 그리드 발표를 포함한다. 수동 모드의 결과 대기는 로컬 벽시계 최대 5분이며 버튼/타임아웃은 같은 단발성 전환을 사용한다. 되감기는 로컬 진행 상태만 초기화한다. 예선 기록의 동률 정렬은 공식 그리드와 같은 출발 순서 기준이다.

미출발 회색/`—`, 주행 상태, 2초 노란 기록 갱신+0.6초 페이드, 후방/정면/측면/전체샷, 최근 최고 기록·사고·마지막 완주자 우선 중계를 제공한다. 결과 표와 수동 진행 버튼은 전체화면에서도 제공하며, 모바일 펼친 기록표에도 강조를 적용한다. 독립 리플레이와 연속 재생을 모두 유지한다.

기본 3랩과 기존 기본 속도를 유지했다. 10랩/2배 실제 속도/새 그리드/운영 시즌/관리자 인증/서버 동기화/실제 베팅은 미구현 범위다. 20:00 / 20:55 / 21:00 KST 일정은 순수 계약 테스트로 보존하며 실제 스케줄러를 실행하지 않는다.

## 해석 및 한계

- 사용자의 Phase 2-A RTX 4070 SUPER 평균 29.999FPS는 과거 하드웨어 결과다. 이번 v0.5의 결과로 전용하지 않는다. 당시 JSON 캔버스는 1278×719였으며 전체화면 해상도 성능은 미확인이다.
- 새 CI의 WebGL 제출 간격/FPS는 Linux Chromium + SwiftShader 결과다. 물리 Windows GPU, 광학 디스플레이 프레임, GPU 실행시간/VRAM 측정과 다르다.
- 33.3ms 초과율은 원시 지표다. 정상 30FPS 간격도 33.333ms이므로 이 비율만으로 프레임 드롭을 판정하지 않는다. 50ms 초과율을 함께 본다.
- 같은 runner에서 고정 Phase 2-A와 v0.5를 순서대로 측정한다. 규칙/기본 Seed/카메라 장면이 다르므로 순수한 코드 한 줄의 인과적 벤치마크는 아니다.
- 6분 반복 재생은 3랩 기록의 교체/반복이다. 미래 10랩이나 무기한 안정성을 인증하지 않는다. JS heap 변화와 살아 있는 WebGL 리소스 수를 구분한다.
- 모바일은 Chromium viewport이며 실제 Android/iOS 기기 검증은 아니다. Windows job은 PowerShell 실행기·SHA·포트 충돌을 검증하며 Windows Chrome의 하드웨어 30FPS 인증은 아니다.

## 재현 및 Windows 관람

1. 최종 CI의 `galactic-racing-v5-demo` ZIP 전체를 **새 폴더**에 압축 해제한다.
2. `START-RACING.bat`를 실행하고, 상단 `PHASE 2-B / v0.5` 및 Build SHA를 확인한다. Node/Python/API 키는 필요 없다. 관리형 Windows의 스크립트 제한은 우회하지 않는다.
3. 기존 서버가 43874를 사용하면 종료하거나 `START-RACING.bat -Port 43875`를 실행한다. 점유된 포트에서는 이전 데모를 자동으로 열지 않는다.
4. `퀄리파잉 다시보기`에서 자동/수동 발표를 선택한다. 수동은 결과 발표의 버튼 또는 5분 만료로 한 번만 진행한다. `전체 연속 재생`으로 예선→그리드→본경기→시상식을 연결한다.
5. 기본 `9re-0`의 본경기에서 루크스의 첫 분기는 12.9265초에 진입하고 24.8866초에 합류한다. 수동 선수 카메라로 루크스를 추적할 수 있다. 세부 진입/합류 시각은 ZIP의 `race.json`에 있다.
6. 개발자 성능 패널 또는 `?perf=1`에서 일반 화면과 전체화면/큰 HUD를 각각 30초 이상 재생한 뒤 JSON을 내려받는다. GPU 이름, viewport, renderer.width/height, devicePixelRatio를 함께 확인한다. 앱 JSON의 renderer.width/height는 CSS 크기이며 CI의 `canvasPixels`는 실제 캔버스 픽셀 크기다. 사용자 환경에서 실제 픽셀 크기가 필요하면 Chrome Console에서 읽기 전용으로 `const c=document.querySelector('.scene canvas'); [c.width,c.height]`를 확인한다. 30FPS cap 표시만으로 통과를 판정하지 않는다.

로컬 실행: `pnpm racing:build:v5`, `pnpm racing:watch:v5`. 실제 스크린샷은 Actions의 `galactic-racing-v5-screenshots`, 원시 성능은 `galactic-racing-phase2b-performance`에 있다. CI 아티팩트 보존 기간은 14일이다. 사용자에게 전달한 ZIP은 해당 CI 아티팩트 원본과 SHA-256을 비교한다.

## 실패했던 검사와 보완 기록

- 초기 좁은 분기는 본선 도로 폭과 과도하게 겹쳐 더 넓은 20%→40% 곡선으로 교체하고 40k를 다시 실행했다. 예전 밸런스 결과는 최종 값이 아니다.
- 첫 브라우저 실행은 250ms seek 양자화 때문에 다음 라운드 시작 전을 촬영했다. 테스트가 실제 단계 안으로 이동하도록 수정했고 라운드 경계 자체를 느슨하게 만들지 않았다.
- 중간 성능 실행 `41267061375`는 서로 다른 Seed/시점의 WebGL 버퍼 수 비교에서 실패했다. 지연 할당되는 효과를 같은 장면으로 오인한 검사였다. `9bd486ab`부터 동일 Seed의 새 renderer/시작 시점으로 정규화하고, 모든 교체 후 이전 context 소실·새 context 단일성·같은 장면의 버퍼/텍스처 안정성을 검사한다. 실패해도 원시 체크포인트를 먼저 저장한다. 이 변경을 앱의 메모리 누수를 고쳤다고 표현하지 않는다.
- 전체화면 전환 직후 캡처에 HUD만 보인 장면이 있어 `50fecc0a`부터 실제 캔버스 PNG의 색 다양성 검사를 추가했고, `874b0098`에서는 HUD를 검사 이미지에서 가려 3D 없는 HUD만으로 통과하지 않게 했다. 리사이즈/단일 RAF 완료를 제한된 시간 동안 기다린 뒤 검사하며, DOM 존재만으로 시각 PASS를 선언하지 않는다.

브라우저의 5분 만료 검사는 Playwright의 Date 시계를 300,001ms 전진시켜 수행한다. 도메인 테스트는 299,999ms 차단/300,000ms 단발 전환을 별도로 검증한다. 실제로 관리자가 5분간 기다리는 운영 방송이나 분산 서버 타이머를 검증한 것은 아니다. 라운드/연속 재생 검사는 실제 UI 조작과 경계 직전 탐색 후 재생으로 전환을 확인하며, 전체 7분 30초 예선을 매번 처음부터 실시간으로 관람했다는 뜻은 아니다.

- `9bd486ab`의 6분 결과에서는 모든 12회 교체가 context 1개 / 이전 context 소실을 만족했지만, 한 체크포인트의 버퍼가 262→274로 달라 동일 장면 검사에 실패했다. 검사 도중 `본경기 다시보기`가 잠깐 자동 재생되어 첫 tick 효과를 할당할 수 있었다. `557a08d0`은 이 재생 조작을 제거하고, 새 context + 정지 버튼 + 진행 0 + wide 카메라가 모두 확인된 최초 장면을 비교한다. 동일 장면 버퍼/텍스처 수의 엄격한 비교는 유지한다.

- `557a08d0`은 리플레이 교체 직후 0 위치/정지/wide 조건에서 타임아웃을 보고했다. 코드에서 이전 RAF가 React의 지연된 effect cleanup 전까지 새 `playhead`를 덮어쓸 수 있는 위험 경로를 확인했다. 이것이 해당 CI 타임아웃의 실제 원인인지는 당시 확인하지 못했다. `fbb28079`는 새 기록을 설치하기 전에 기존 clock을 dispose하고, 취소된 로딩 결과도 설치하지 않는다. 이미 큐에서 빠진 이전 콜백도 dispose 후에는 새 위치를 덮어쓰지 못하는 단위 회귀와, 뷰포트별 실제 기록 교체 6회를 추가했다. 실패 시 검사 상태/화면과 부분 장시간 결과를 저장한다. 고정 Phase 2-A baseline만 교체 후 비재생 seek로 정규화하며 새 후보에는 그런 보정을 하지 않는다.

- `fbb28079`의 새 브라우저 교체 검사도 초기화 복합 조건에서 실패했다. 이전 단위 회귀 PASS를 실제 교체 성공으로 확대 해석하지 않았다. `e5fea118`에서 실패 순간의 진행 바 값·카메라·정지 상태·로컬 재생 세션·화면을 함께 수집해 원인을 구분한다.

- `e5fea118`은 실패 상태를 실제로 확보했다: 새 normal Seed, wide/paused는 맞았지만 `segment=qualifying`, 진행 바 449500ms(250ms 단위), 실제 시각 449587ms로 이전 정상 경기 세션을 복원했다. 로컬 사례 전환은 새 경기 시작이어야 하지만 초기 페이지 로딩과 같은 복원 규칙을 사용한 것이 확인된 원인이다. `ff1efab6`은 세션 복원을 최초 페이지 로딩에만 허용한다. 각 사례 교체 전에 일부러 대상 Seed의 이전 예선 세션을 저장하는 브라우저 회귀 6회와, 별도 페이지의 정상 60초 이어보기 회귀를 추가했다.
